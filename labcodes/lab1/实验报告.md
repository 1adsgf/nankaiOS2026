## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

本章主要讲解最小可执行内核和启动流程，让Kernel在Qemu模拟器上运行并且能够打印出一行文字。

其流程可以分为以下两条：

1. **内核的内存布局和入口点设置** 操作系统自己做不到"把自己加载到内存"（不能拽着自己的头发离开地面）。所以必须有一个"先锋队"——bootloader。在 QEMU 的 RISC-V 虚拟平台上，这个角色由固化在 `0x80000000` 的 **OpenSBI 固件**担任。编译链接生成的机器指令中，访存地址在链接时就已被写成**绝对地址**（地址相关代码），所以内核必须被放到链接脚本约定的物理内存以地址 `0x80200000`开头的区域上；并且内核镜像的**第一条指令必须落在这个地址上**，OpenSBI 才能把控制权交给操作系统内核。
2. **通过 OpenSBI 封装输入输出函数** 内核里没有 glibc（直接调用C语言库构成了一个**鸡生蛋蛋生鸡**的过程，是不合理的），`printf` 无从谈起。于是必须从**最底层的 SBI 服务**（M 模式）出发，用 `ecall` 一层层封装：`sbi_console_putchar` → `cons_putc` → `cputch` → `cprintf`。

### 2.2 功能的逐步实现

| 步骤  | 实现内容                                                                                             |
| --- | ------------------------------------------------------------------------------------------------ |
| 1   | **链接脚本 `tools/kernel.ld`**：`BASE_ADDRESS = 0x80200000`，`ENTRY(kern_entry)`，指定程序的入口               |
| 2   | **汇编入口 `kern/init/entry.S`**：定义 `kern_entry`，`la sp, bootstacktop` 设置内核栈，`tail kern_init` 跳入 C   |
| 3   | **C 入口 `kern/init/init.c`**：`memset(edata, 0, end - edata)` 清 `.bss`，打印信息，死循环                    |
| 4   | **输出子系统自底向上封装**：`libs/sbi.c` → `kern/driver/console.c` → `kern/libs/stdio.c` + `libs/printfmt.c` |
| 5   | **构建系统 `Makefile` + `tools/function.mk`**：交叉编译 → 链接成 elf → `objcopy` 成 bin → QEMU 加载运行           |
| 6   | **GDB 远程调试**：`make debug` + `make gdb`，跟踪复位向量到内核入口                                               |

## 六、实验总结与收获

### 对操作系统的理解
这次 lab1 让我第一次真正接触操作系统内核的启动过程，以前只是理论上知道“操作系统管理硬件”，但具体它怎么被加载、第一条指令在哪里、怎么和固件交互，一直很模糊。通过亲手编译、运行、调试一个最小可执行内核，很多抽象概念终于落地了。

我搞清楚了 RISC-V 从上电到内核启动的完整流程：加电后 CPU 从 0x1000 的复位向量开始执行，那里是一小段固件，负责把 OpenSBI 的入口地址装入寄存器并跳过去；OpenSBI 运行在 M 模式，完成硬件初始化后，把内核加载到 0x80200000，再以 S 模式跳过去；内核的第一条指令是 entry.S 里的 la sp, bootstacktop，它设置好内核栈，然后通过 tail kern_init 进入 C 语言入口。这条链每一步都缺一不可，让我对“bootloader”和“固件”的作用有了直观认识。

我还理解了交叉编译和链接脚本的意义。在 x86 上编译 RISC-V 代码需要专门的交叉编译器；链接脚本 kernel.ld 指定了内核加载地址和入口点，把 entry.S 放在镜像最开头，才保证 0x80200000 处正好是 kern_entry。以前写 C 程序从没关心过链接脚本，这次算是补上了重要一课。

调试过程中，我对栈的作用也有了更深的理解。内核入口处 sp 是 OpenSBI 留下的临时栈值，并不可靠，所以 entry.S 必须先把它换成内核自己的栈，才能在 C 函数里安全使用。这个细节让我明白，函数调用不是理所当然的，它依赖一个正确的栈环境。

此外，cprintf 的实现链也让我印象深刻：从 ecall 陷入 M 模式，到调用 OpenSBI 的字符输出服务，再层层封装成 cons_putc、cputs、cprintf。这让我看到，内核在“一无所有”的环境下，是如何从最底层的硬件接口一步步构建出可用的输出功能的。
### AI 协作开发的经验
这次实验也是我第一次在开发过程中系统地使用 AI 工具。我用 VS Code 加 Cline 插件，接入 DeepSeek 模型，让它帮我读代码、改 Makefile、分析 entry.S。整体感受是：AI 确实能提高效率，但前提是你会用，并且不能完全依赖它。

比如，一开始 make qemu 跑不起来，输出里 Domain0 Next Address 是 0x0，我让 Cline 帮我分析，它建议把 Makefile 里的 -device loader 改成 -kernel，问题就解决了。还有阅读 entry.S 时，它能把 la sp, bootstacktop 和 tail kern_init 的作用解释得很清楚，帮助我快速理解汇编代码。这些场景下，AI 像一个随时在线的助教，省去了大量查资料的时间。

但我也踩了不少坑。配置 Cline 时，由于之前设置过代理，它一直报 ECONNREFUSED 127.0.0.1:7897，后来清掉 Cline 缓存、退出加速器、重设配置才解决。这让我意识到，AI 工具本身也依赖环境，网络、代理、API Key 任何一个环节出错，它都干不了活。另外，Cline 有时会执行 PowerShell 命令，而我的项目在 WSL 里，命令类型不对，需要手动拒绝并纠正。这说明 AI 并不总是理解上下文，需要人来把关。

更重要的是，我学会了审查 AI 的输出。Cline 生成的代码或分析有时过于深入，甚至超出我的知识水平，如果直接抄进报告，老师一眼就能看出不是自己写的。所以我的做法是：让它帮我理解，但结论用自己的话重新组织；改文件时看 Diff，确认无误再同意；关键操作自己动手跑一遍，确保真的懂了。

总的来说，AI 是一个强大的辅助工具，它能帮你省去重复劳动、快速定位问题，但它不能代替你思考。只有自己理解了操作系统的基本原理，才能判断 AI 说得对不对，才能真正把它的输出变成自己的知识。
